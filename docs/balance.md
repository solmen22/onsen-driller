# バランスのシミュレーターと目標表の判定（BL-031・BL-033）

gdd §8（バランス検証）の実装の説明。数値の調整の手順は gdd §8-4、判定の規則の元は gdd §8-6 と QA のテスト戦略 §3-3。

## コマンド

| コマンド | 中身 | 終了コード | 所要時間（手元の Windows） |
|---|---|---|---|
| `npm run test` | `tests/balance/` の短縮版: 標準・放置 × シード 1〜8 × 1 時間の判定、標準ボットのハッシュの固定値、20 時間の決定性、安い順・ランダムのシード 1 の 20 時間（例外・健全・詰み。BL-032） | テストの結果 | 約 10 秒（並列の中） |
| `npm run test:balance` | 標準・アクティブ・放置・安い順・ランダム × シード 1〜8（1 本目は 20 時間、残りは 1 時間）を流し、目標表で判定し、`reports/balance/` にレポートを書く。#23（step の処理時間）も測る | 範囲外（受け入れていない）か #23 が 50µs 以上か、完全な詰み（10 分以上）があれば 1 | 約 13 秒 |
| `npm run sim` | `test:balance` と同じ一式のレポートに加えて、PoC からの計測（同じシードで同じハッシュ・刻み幅の差・#23）を端末に出す | 常に 0 | 約 20 秒 |

- 引数（`test:balance`）: `--seeds 1,2,3`（既定 1〜8）・`--long 20`（1 本目の時間）・`--short 1`（残りの時間）・`--out reports/balance`
- 引数（`sim`）: `--seed 1`（長く流すシード）・`--hours 20`・`--step 1000`・`--out`
- `reports/` は git の対象外（`.gitignore`）。CI・毎晩のジョブは成果物として保存する（nightly.yml の `balance-report`）

## ボット（gdd §8-2。`tools/sim/bots.ts`）

| ボット | 手動の打撃 | 買い物の間隔 | ご褒美（BL-058 の後） |
|---|---|---|---|
| 標準（目標表の基準） | 自動掘り（毎秒 2 打）。最初の強化の前は毎秒 2 タップ | 5 秒 | 広告で毎回 |
| アクティブ | 長押し（毎秒 4 打）を最初から | 2 秒 | 広告で毎回 |
| 放置 | 毎秒 0.3 タップだけ（自動掘りは使わない） | 60 秒 | 受け取らない |
| 安い順（BL-032） | 標準と同じ | 5 秒 | 受け取らない |
| ランダム（BL-032） | 毎秒 1 タップだけ | 10 秒 | 無作為 |

- 買い方（標準・アクティブ・放置）: 投資効率（増える収入 ÷ コスト）が最大のものを買う。最良が買えなければ、効率が最良の 50% 以上で買えるものを買う。道具の進化は買えるようになったらすぐ買う。
- 買い方（安い順）: 道具と候補のうち、いちばん安いものを買う。それが買えなければ待つ。枠は標準と同じ。
- 買い方（ランダム）: 買えるもの（道具・候補）から無作為に、買えるものがなくなるまで買う。枠も、見つけた源泉の 1 つを無作為な枠につなぐ。乱数はボット専用（シードから決まり、ゲームの乱数とは別）。詰み・例外の検出用。
- 完全な詰み: 買えるものがなく、手動を含む収入も 0 の状態。毎ステップの始めの状態で数え、`test:balance` は全ボット・全シードで 10 分以上続いたら失敗にする（BL-032）。
- 「収入」の見積もりは、掘削（そのボットの打数 × 威力 ÷ HP × 価値の期待値）＋入湯料。泉質の効果とお客さん（Lv10 のポンプで来るお客さんを含む）を入れて測る。
- 枠: 見つけた源泉が枠の数以下なら全部つなぐ。多ければ、収入が最大になる組み合わせ（最大 5 通り）をつなぐ。つないである源泉はその枠に残す。
- 転生: 湯の華が前回の 1.5 倍以上（初回は 30 以上）、または最深の伸びが 2 分止まったら（本実装の規則と地形の選び方は BL-032）。
- 広告なし（BL-058 のご褒美の後）・構成別 3（S3 の転生の本実装・木の後）は BL-032 の残り。「8 時間放置 → 復帰」のシナリオは、オフラインの付与が core に入ってから。

## 判定の方法（`tools/sim/targets.ts`）

1. **シード 1〜8 で流し、シードごとの値の中央値で判定する**（値が 8 個なら、真ん中の 2 つの平均）。
   - 理由: ボットの買い物は 2〜60 秒ごと、刻みは 1 秒なので、出来事の時刻はシードで数秒〜数十秒揺れる（例: #8 はシード 1〜8 で 13:23〜14:04、#6 は 3:55〜4:30）。1 本のシードで判定すると、1 秒の差で合否が変わる。
   - 範囲の端に追加の許容幅は持たせない（中央値そのものを範囲と比べる）。レポートにはシードごとの値も出すので、端に寄っている項目は分かる。
2. 出来事が半分より多いシードで起きていなければ（その時刻まで届かない）、失敗にする。
   - 出来事の時刻の項目（`event: true`。#2〜#8・#10・#12・#13）では、実行の長さが目標の上限以上なのに起きなかったシードを「範囲より遅い」（+Infinity、レポートでは「未達」）として中央値に入れる。起きた速いシードだけで合格しないため（8 本中 4 本が未達なら中央値が未達で失敗。BL-122）。
   - 実行が目標の上限より短く、起きなかったシード（その時刻まで流していない）と、時刻でない項目（#17 など）の値がない実行は、中央値から除く。
3. **保留**（`kind: 'pending'`）: まだ入っていない要素（改良・ご褒美・転生の本実装・地形・エンディング・ボットの 6 本）に依存する項目。値が出せるものは参考に出すが、失敗に数えない。依存するチケットが done になったら `kind: 'judge'` に変える。
4. **外部**（`kind: 'external'`）: #1 は E2E（E1）、#23 は `test:balance` の計測（本判定は性能テストの BL-079）。#22（数値の健全性）は全ボット・全シードの実行中の検査と L1 の不変条件で判定する。
5. **受け入れ**（`ACCEPTED`）: 範囲外を意図して受け入れる項目。理由・承認者・期限（直すチケット）を書く（gdd §8-6: 技術リードが承認。**#20・#21 は QA リードの同意も要る**）。受け入れた項目は、判定に使った値が**受け入れる幅**（`bounds`。受け入れたときの値の幅に余裕を足す。#8 は 12:00〜20:00、#10 は 15:00〜40:00）の中で、かつ半分以上のシードで値があるときだけ失敗にしない（幅の外・値がなければ失敗。BL-122）。レポートの「範囲外を受け入れた項目」に幅と一緒に必ず出る。範囲内に戻ったら、合格のまま「範囲内に戻った受け入れ（ACCEPTED から消す）」に出る（`test:balance` は警告を出す）。期限のチケットで数値を直したら消す。
6. 範囲のない項目は ±20% を許す（gdd §8-6。今の 24 項目にはない）。

## 見張り

- `tests/balance/sim-smoke.test.ts` の `STANDARD_1H_SEED1_HASH`: 標準ボット・シード 1・1 時間のハッシュの固定値。core・content・ボットのどこかを変えて結果が変わると赤になる。**数値やボットを意図して変えたときは、この値を更新し、理由と `npm run sim` のレポートの差を PR の説明に書く。**
- 同じシードを 2 回流すと、20 時間の結果（ハッシュ・最深・転生の回数）が同じ。
